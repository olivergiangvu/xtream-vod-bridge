# v0.5g Same-port Canary at HTTPS 18450

The existing nginx :18450 public vhost is the only HTTPS entrypoint. Production paths /admin/, /admin-signin/, /a/ and /play/ must not be changed. Canary routes are /canary/admin/, /canary/admin-signin/, /canary/a/ and /canary/play/ and are temporary for Safari QA.

## Security limits

Canary and production are on the same browser origin. Cookie names and Paths are isolated, but scripts on the same origin are not securely isolated. Restrict every Canary nginx location to approved LAN/VPN source IPs. Do not open any new ASUS router WAN port. Canary stays in its internal Docker network with independent SQLite, dummy IPTV provider config and no egress.

## Staged deployment

1. Stage 4A Canary session isolation is confirmed PASS on HomeDocker. The production Admin/Playback images and persistent data are unchanged.
2. PR #44 implements opt-in XTREAM_URL_PREFIX=/canary and frontend-relative login/Lock navigation. Root-path production defaults are preserved.
3. Run the pinned, read-only canary/stage4c_sameport_preflight.py to discover the actual nginx public vhost source file, its SHA256, host LAN CIDR and live Canary container IPs. It must not modify nginx.
4. Run the pinned **Stage 4D preview-only** `canary/stage4d_route_review.py` before any container or nginx write. It compares the live production vhost to its exact approved SHA256, reads the live Docker network/IPs and health, downloads and verifies the immutable Canary nginx route template, and generates a temporary candidate vhost. The scratch nginx -t runs using `-c` on a private temporary config; it neither includes the template in production nor reloads nginx. It proves deleting the proposed single include directive restores the original vhost **byte for byte**, then destroys the scratch files. `STAGING_NGINX_SYNTAX=NEEDS_CONTEXT_REVIEW` must be investigated; it is not a production syntax pass.

   HomeDocker validation (2026-10-14): Canary Admin HostConfig still records `127.0.0.1:18770 -> 8768`; Canary Playback records `127.0.0.1:18769 -> 8767`. Both containers are attached only to the internal Canary network, both NetworkSettings.Ports entries are null, and `docker port` produces no mappings. These are **dormant configured loopback binds**, not live publications. Stage 4D checks actual effective publication and docker port separately, rejects any active mapping, and also refuses dormant non-loopback bind metadata. Docker container recreation may activate stale bindings if they remain in the Compose model; require an explicit no-ports Compose config review before any recreation.

   The template is a proposal, not a deployed security boundary. Do not deploy it until checking ASUS WAN forwarding/SNAT and LAN/VPN access. Always rediscover Canary IPs after Compose recreates containers, because dynamically allocated Docker IPs can change. Also ensure the host is not suffering sustained CPU saturation during image build or nginx reload.
5. Only after review, run pinned canary/upgrade_same_port_containers.sh. It overlays the new Admin route helper and JS on the isolated Canary Admin image, and recreates Canary Playback with PUBLIC_BASE_URL set to https://olivergiangvu.asuscomm.com:18450/canary. It backs up the existing Canary Compose override and attempts automatic rollback on errors.
6. Add only scoped Canary nginx locations inside the existing public :18450 server block; use its existing TLS certificate. Map /canary/admin/ to Canary Admin :8768, /canary/admin-signin/ to its /gateway/, /canary/a/ to Canary Playback /a/, and /canary/play/ to /play/. A separate nginx-internal auth_request subrequest to Canary Admin must verify the distinct Canary session cookie.
7. Refuse all other /canary/ paths, disable access logs on token-bearing requests, preserve original production locations, run nginx -t, and provide a byte-for-byte backup and rollback before reloading nginx.
8. Provision a unique Canary owner passphrase through docker exec -it xtream-vod-canary-admin python -m admin_auth set-password. Enter it interactively; do not put it in shell history or chat.
9. Test Safari native login -> /canary/admin/, User RBAC, My Sources, My Manifests, Lock -> /canary/admin-signin/, and unchanged production playback and login.
10. Real IPTV network access needs a separate approved egress and provider compatibility stage.

The testing prefix will be removed on final production promotion, which needs an independent acceptance and rollback decision.
